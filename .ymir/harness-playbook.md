# Harness Generation Playbook — vietcham-data-ops

> Generated by Ymir on 2026-09-17. This playbook DRIVES an LLM to generate the
> project harness. Ymir itself wrote no harness files — only this spec and
> `.ymir/harness-profile.yaml`.
>
> **How to use:** read `.ymir/harness-profile.yaml` for decisions, then follow
> the per-concern sections below. Each section lists the profile keys it
> consumes (Inputs), the generation Steps, and how to Verify the result.
>
> Each section opens with a **Why / Findings** line recording the rationale and
> what the codebase scan saw — context for the engineer/LLM; not an action.

---

## ⚠️ Read first — this harness deviates from Ymir's stock `any` mode

`target_agent.value` is `any`, but the stock `any` generator (single `AGENT.md`,
all rules inline, no `.claude/` at all) is **not** what this project wants, and
applying it would silently destroy a design the repo already chose and
documented. The user approved this deviation during the interview:

| Stock `any` | This harness |
|---|---|
| `AGENT.md` at root | **`CLAUDE.md`** at root, with the existing `AGENTS.md` → `CLAUDE.md` symlink **preserved** |
| rules embedded inline | rules in **`.claude/rules/*.md`**, path-scoped |
| no pointer to rules | **explicit rules index in `CLAUDE.md`** — Claude auto-loads them, Codex does not, so the pointer is what makes it agent-neutral |
| wiki guarded by CI | wiki guarded by CI *(unchanged — a PreToolUse hook would not bind Codex)* |

**Never replace the `AGENTS.md` symlink with a copy.** `CLAUDE.md` says why: the
legacy repo kept two byte-identical files and needed a sync step to stop them
diverging. Removing the failure mode beats policing it.

## rules → native rules files

- **Why / Findings:** The conventions are already written and still get violated at specific paths — float creeping into an amount, a mock standing in for a real in-memory implementation, a real client name in a tracked fixture. CLAUDE.md states them always-on, so they are loudest when irrelevant and no louder than usual at the moment of the edit — repo scan: present-strong (CLAUDE.md + 3 ADRs + unusually good module docstrings) but no `.claude/rules/` and no `.editorconfig`, so nothing is path-scoped. Considered: keep-everything-in-CLAUDE.md, docs/rules.md, split-for-context-economy-instead-of-enforcement.
- **Target:** `.claude/rules/` — one file per `concerns.rules.files[]` entry, i.e. `data-integrity.md`, `raw-lake.md`, `tests.md`, `pii.md`, `deployment.md`. Treat each file as its own artifact for keep/merge/overwrite and back up per file.
- **Inputs:** `concerns.rules.files[]` (each `{name, paths, obey[], avoid[]}`), `target_agent.deviation.rules_location`
- **Steps:**
  1. For each `files[]` entry, create `.claude/rules/<name>.md`.
  2. Add YAML frontmatter listing each glob from `paths` (every entry here is
     scoped; none is always-on):

     ```markdown
     ---
     paths:
       - "<glob>"
     ---
     ```
  3. Add a top **"NEVER"** list — one bullet per `avoid[]` item, verbatim in
     meaning. These are prohibitions, not preferences; do not soften them into
     "prefer not to".
  4. Below it, phrase the `obey[]` items as the positive rules to follow.
  5. Give each file one or two sentences of *why*, drawn from the existing
     module docstrings (`vcdo/core/money.py`, `vcdo/core/names.py`,
     `vcdo/lake/store.py`) and `CLAUDE.md`. Per the repo's own convention, a
     constraint without a recorded reason gets "simplified" away by the next
     reader — so no rule ships without one.
  6. Do **not** restate these rules in `CLAUDE.md`; the `claude_md` section
     below removes the duplicates. One owner per rule.
- **Verify:** every `files[]` entry has a matching `.claude/rules/<name>.md`;
  each file's frontmatter `paths` matches the profile exactly; every `avoid[]`
  item appears in its file's NEVER list.

## lint → linter config

- **Why / Findings:** ruff needs no change — it is conservative on purpose and every ignore carries a written reason. The real gap is pyright: configured in `pyproject.toml` (standard mode, pointed at `.venv-tests`) but neither pinned in `requirements-dev.txt` nor run by `make verify`, so the config is aspirational — repo scan: present-strong (ruff `E,F,I,UP,B,SIM`, reasoned ignores `E731`/`B905`/`SIM300`, line-length 110, isort first-party `vcdo`, `make lint` = check + format --check); weakness: `[tool.pyright]` exists but pyright appears in no requirements file and no make target. Considered: gate-pyright-immediately, keep-pyright-editor-only-and-document-it, widen-ruff-select-to-RUF-PL-ANN-PTH-S.
- **Target:** `pyproject.toml` (`[tool.ruff]`, existing — leave as-is) and `requirements-dev.txt` (add the pyright pin).
- **Inputs:** `concerns.lint.tool`, `concerns.lint.style`, `concerns.lint.type_checker`
- **Steps:**
  1. **Change nothing in `[tool.ruff]`.** It is already correct and its ignores
     are individually justified. Widening `select` was considered and rejected.
  2. Add a pyright pin to `requirements-dev.txt`, in a commented block matching
     the file's existing voice, stating that it is pinned so the configured
     type checker resolves identically on every machine, and that it is **not
     yet part of the gate**.
  3. **Re-resolve the pins as a set, in one `pip install`** — never package by
     package. `requirements-dev.txt` records why: pinning independently once
     produced an unsatisfiable file here, when a hand-chosen botocore
     conflicted with what dlt's s3fs needed, and the break only surfaced on a
     clean venv rebuild.
  4. Do **not** add pyright to `make lint` or `make verify` yet. The CI section
     runs it non-blocking; gating is decided from that measurement.
  5. Add a one-line comment above `[tool.pyright]` in `pyproject.toml` recording
     that it is intentionally outside the gate pending that measurement — so the
     next reader does not "fix" it by wiring it in.
- **Verify:** `make lint` runs clean (`ruff check .` and `ruff format --check .`
  both green), and `make venv` rebuilds from scratch after `make clean` without
  a resolver conflict.

## CI lint → CI workflow

- **Why / Findings:** `make verify` is the gate but nothing enforces it — it holds only when someone remembers. The Makefile already anticipates CI: its comment on `itest` says the plain `test` target deliberately does not source `.env` "or CI cannot run it", so the gate was built to run on a machine with no stack and no secrets. CI is collecting on that design — repo scan: missing (GitHub remote `muitneliss/vietcham-data-ops`, no `.github/` at all). Considered: make-verify-only, lint-only, skip-ci.
- **Target:** `.github/workflows/ci.yml`
- **Inputs:** `project.runtime`, `concerns.ci.provider`, `concerns.ci.runs[]`, `concerns.ci.triggers`, `concerns.ci.excludes`, `concerns.lint.type_checker`, `concerns.wiki.guard`
- **Steps:**
  1. Create `.github/workflows/ci.yml` triggered on push to `main` and on
     `pull_request`.
  2. One job on `ubuntu-latest` with Python 3.12 (`actions/setup-python`),
     caching pip against `requirements-dev.txt`.
  3. Install dependencies **as a set**, mirroring the Makefile's `$(VENV)/.stamp`
     recipe: `pip install -r requirements-dev.txt` then `pip install -e .`.
  4. **Blocking step:** `make verify`. Let the Makefile own the command — CI must
     not spell out `ruff check` separately, or the two definitions of "the gate"
     drift.
  5. **Non-blocking step:** `pyright`, with `continue-on-error: true`. This is
     the measurement the `lint` decision is waiting on, taken continuously
     instead of once. Do not let it fail the build.
  6. **Blocking step:** the wiki guard — see the `wiki` section, step 2.
  7. Do **not** run `tests/monitors/` or `tests/integration/`. Monitors bind to
     live data and deployed services — red there means data drift, not a code
     defect — and integration needs the docker stack plus secrets. `make verify`
     already excludes both; do not reintroduce them with an explicit path.
  8. Set `permissions:` to the minimum the job needs (`contents: read`).
- **Verify:** the workflow is valid YAML, runs the same command `make verify`
  runs locally, and contains no reference to `tests/monitors` or
  `tests/integration`.

## release → release-please workflow

> Not one of Ymir's five concerns; captured under `concerns.ci.release` at the
> user's request during the interview.

- **Why / Findings:** Gives a versioned marker to deploy AT, which the repo lacks — "which build is on the server" is unanswerable today — repo scan: missing (no CHANGELOG.md, no tags in use, `[project].version = "0.1.0"` static in `pyproject.toml`, nothing published). Considered: release-please-plus-dokploy-deploy-on-tag, changelog-only-no-version-bump, manual-make-release-target.
- **Target:** `.github/workflows/release-please.yml`
- **Inputs:** `concerns.ci.release.*`
- **Steps:**
  1. Create `.github/workflows/release-please.yml`, triggered on push to `main`,
     using `googleapis/release-please-action` with `release-type: python`.
  2. It maintains a release PR; merging that PR bumps `[project].version` in
     `pyproject.toml`, writes `CHANGELOG.md`, and cuts a GitHub release + tag.
  3. `permissions: { contents: write, pull-requests: write }` — and nothing else.
  4. **Do not add any deploy step.** `concerns.ci.release.deploys` is `false` by
     decision: a merged release PR must not become a production change. Shipping
     stays a human action through the `dokploy` skill, which keeps the
     "API is the only channel" rule under a human hand and keeps a production
     credential for a shared host off GitHub.
  5. **Do not add a publish step.** Nothing here goes to PyPI.
  6. **Prerequisite — Conventional Commits.** History is not conventional
     (`Phase 1: HubSpot vertical slice…`, `Drop Airbyte: …`). release-please
     rewrites nothing; it simply finds nothing to release until commits read
     `feat:` / `fix:`. This is handled by the `conventional-commits` steer in
     the `claude_md` section. A commitlint job was deliberately **not** specced —
     a gate on commit messages in a single-operator repo costs more than the
     silent absence of a release PR, which is feedback enough.
- **Verify:** the workflow is valid YAML; it contains no deploy or publish step;
  its `permissions` block grants only `contents: write` and
  `pull-requests: write`.

## wiki / context → LLM-maintained wiki

- **Why / Findings:** One body of knowledge lives in no file in this repo: the expensive findings from the legacy system — the raw-lake deduplication ratio, the instability of Gmail attachment ids, the Xero credit-note payment quirk, and the volatile-key identity failure that repointed 178 of 358 mappings at the wrong company. Today they are referenced in prose and readable only by opening another repo on disk — repo scan: present-weak (docs/ is strong human documentation — README index, 3 ADRs, contracts/ and runbook/ planned — but there is no keyword-searchable agent context store and no distillation of the legacy reference).
- **Target:** `wiki/`
- **Inputs:** `concerns.wiki.enabled` (run only when `true`), `concerns.wiki.collection`, `concerns.wiki.boundary`, `target_agent.value`
- **Steps:**
  1. **Scaffold** — a single CLI call, never hand-edited files. `target_agent.value`
     is `any`, so scaffold **without** the hook:

     ```bash
     node "$SKILL_ROOT/hooks/ensure-wiki-binary.mjs"
     "$SKILL_ROOT/wiki-cli/bin/wiki" --root ./wiki init --no-hook
     ```

     `$SKILL_ROOT` is the Ymir skill's root directory (the one containing
     `SKILL.md`). Idempotent; on success the last line is `wiki valid`. If it
     errors, stop and report. No `.claude/settings.json` and no PreToolUse hook
     are written — a hook would not bind Codex, and half-enforcement reads as
     enforcement.
  2. **Wiki guard** — add a blocking step to `.github/workflows/ci.yml`:

     ```
     wiki check --error-on-untracked-sources
     ```

     Agent-independent enforcement equivalent to the hook. A wiki page asserting
     a fact with no tracked source fails the build rather than quietly becoming
     folklore.
  3. **Record the ownership boundary** in `wiki/SCHEMA.md` (or the wiki's index
     page) and mirror it in `CLAUDE.md`:
     - `docs/` holds **decisions we made** — numbered, dated, immutable,
       superseded rather than edited.
     - `wiki/` holds **facts we learned** — measured, updatable, searchable.
     - An ADR may cite a wiki page for the measurement behind it. A wiki page
       never records a decision.
     This boundary is the whole reason a second knowledge store is acceptable
     here; without it, `wiki/` becomes a drifting duplicate of `docs/`.
  4. **PII binds here exactly as it binds to `docs/`.** The legacy distillation
     is about real clients. Pages use CASE-IDs; real names never enter git. The
     `pii` rule file's `docs/**` scope should be extended to `wiki/**` when this
     concern is applied.
  5. **Tell the user** the qmd one-time setup (also in `wiki/SCHEMA.md`):
     `qmd collection add ./wiki --name vietcham-data-ops-wiki`. Search is
     keyword-only (BM25) — no `qmd embed`; re-run `qmd collection add` to refresh
     after adding pages.
- **Verify:** `"$SKILL_ROOT/wiki-cli/bin/wiki" --root ./wiki validate` prints
  `wiki valid`.

## CLAUDE.md → steering file

- **Why / Findings:** Once the rules live in `.claude/rules/`, keeping full copies in CLAUDE.md gives every rule two owners — and the next edit updates one of them. That is precisely the drift the AGENTS.md symlink was built to prevent, so the same instinct is applied one level down: one owner per rule — repo scan: present-strong (CLAUDE.md 4.9K, well-reasoned, with an `AGENTS.md` symlink and a note explaining why the symlink exists rather than two synced copies). Considered: keep-CLAUDE.md-complete-and-let-rules-restate-it, minimal-edit-append-pointers-only.
- **Target:** `CLAUDE.md` (root). **`AGENTS.md` is a symlink to it — leave the symlink alone.**
- **Inputs:** `concerns.claude_md.steer[]`, `concerns.claude_md.keeps`, `concerns.claude_md.moves_to_rules`, `target_agent.deviation`
- **Steps:**
  1. **Do not write `AGENT.md`.** Per the deviation, `CLAUDE.md` remains the
     steering file and `AGENTS.md` remains a symlink to it. Verify with
     `test -L AGENTS.md` before and after; never replace it with a regular file.
  2. **Keep** — the sections only CLAUDE.md can carry: what this is; the three
     headline rules as one-liners; the legacy-repo reference and how to treat it
     (reference, not dependency — read before designing, never import); the
     ingestion shape (no ingestion platform, `dlt` is a library, one worker
     container, Kestra for scheduling); the ADR convention; the Python 3.12 /
     `vcdo/` naming note.
  3. **Remove** the detail that now lives in `.claude/rules/` — the Money
     section's specifics, the Tests section's specifics, the Deployment
     section's specifics, and the PII specifics. Replace each with the one-line
     headline plus the rules index entry. The headline rules stay because they
     are the *narrative*; the enforceable detail leaves because it now has an
     owner.
  4. **Add a rules index** — a short table mapping each `.claude/rules/*.md`
     file to its path scope and what it governs. State plainly that Claude Code
     auto-loads these and other agents must read them, which is why the index
     exists at all. This is the one pointer stock `claude-code` mode would call
     redundant; here it is what makes the harness agent-neutral.
  5. **Add the wiki boundary** — `docs/` = decisions, `wiki/` = learned facts,
     with the qmd search command.
  6. **Add `verify-before-commit`** — `make verify` is the gate; run it before
     claiming anything works. Note explicitly that a green `make verify` is not
     evidence the architectural rules held, since ruff cannot see them — which
     is itself rule 2 applied to the harness.
  7. **Add `conventional-commits`** — commit messages use Conventional Commits
     (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`), with a one-line
     reason: release-please derives the version bump and CHANGELOG from them, so
     a non-conventional message silently produces no release.
  8. Keep the file short. It is the map now, not the territory.
- **Verify:** `AGENTS.md` is still a symlink to `CLAUDE.md` (`test -L AGENTS.md`);
  `CLAUDE.md` contains the rules index, the wiki boundary, the `make verify`
  gate and the Conventional Commits directive; and no rule's enforceable detail
  appears in both `CLAUDE.md` and a `.claude/rules/` file.
