# ADR 0155 A Search Ranks Through a BM25 Index per Tenant, Behind a Door

Status Accepted (proposed and accepted 2026-11-06). Amends [[ADR 0123 A Search Ranks Each Kind's Newest Matches, Found Through the Index by the Owner]]: a document search ranks through BM25 indexes instead of a rebuilt vector, and the cap of the newest 100 documents goes; [[ADR 0026: Full-text search over the raw lake]]'s fold, excerpt, GIN indexes and tenant login stay. Context: after [[ADR 0154 The Fold Is Spelled for Speed, and Answers Exactly as Before]] a search still rebuilds each ranked row's vector, so on a production-shaped bench (191,200 documents, 246,200 records, 1 GB) 120 fresh 200k-character documents made every query take 5.25-5.58 s, about 16 s on production's CPU. pg\_textsearch v1.5.1 (PostgreSQL License, Block-Max WAND) ranks from its index and has a PGlite build, unlike ParadeDB pg\_search (AGPL, no Alpine, not in PGlite).

Spike findings: builds on postgres:17-alpine (+3 MB, needs shared\_preload\_libraries); PGlite byte-identical but pins @electric-sql/pglite 0.5.15 and runs PG 18; the tenant login uses the index under RLS (7-8 ms); a shared index leaks corpus statistics between tenants, and to\_bm25query accepts any index name, so a tenant's dbt login could score its own text against another tenant's index (present term -2.17, absent 0: a membership oracle); BM25 missed none of today's matches for 8 queries; page with excerpts p50 377-441 ms, ranking 10-12 ms, worst 1.65 s; ingest +1.1 ms per document; a 10% rewrite grew the index 216 to 362 MB and VACUUM does not shrink it.

Decision: (1) two partial BM25 indexes per tenant on raw\.fold(left(text, raw\.search\_cap())), 'simple' and 'english', created in ops.provision\_tenant and built serially (parallel partial expression builds evaluate every row, timescale/pg\_textsearch#593); (2) the extension in a schema no tenant, BI or scope login can use; (3) a SECURITY DEFINER door raw\.search\_document\_bm25 that derives both indexes from raw\.tenant\_of, returns keys in order without per-row scores (projecting <@> re-scores from text, \~2.3 ms a row), drops non-matching rows, keeps every-term, phrase and negation semantics with an @@ filter, takes the query as a constant, narrows by stream as the candidate lookups do, and falls back to ADR 0123's path while either index is missing or invalid; (4) the newest-100 cap goes and RawSearchResponse.capped changes; (5) English stemming is kept: the door fuses the simple and english orders by reciprocal rank fusion (1/(60+rank), summed) over a bounded, measured head of each list, then filters; (6) records stay on ADR 0123 until measured (statistics are per partition). Operations: our own Postgres image and one restart via Dokploy, CREATE EXTENSION in a migration, PGlite bump, REINDEX CONCURRENTLY by the search-index service above a growth threshold; the image ships one release before anything uses it, tagged by its contents rather than IMAGE\_TAG so a rollback never pulls a tag that was never built. Rejected: shared index, direct extension access, simple-only without stemming, pg\_search, lower caps, stored tsvector. Risks: a young extension with several 2026 corruption bugs (the index is a rebuildable projection), twice the indexes per tenant, no proximity, two-index fusion, records and production-CPU timings unmeasured.
