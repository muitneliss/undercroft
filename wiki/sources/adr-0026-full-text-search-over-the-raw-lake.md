# ADR 0026: Full-text search over the raw lake

The Lake division gets **one search box** over a tenant's whole raw lake -- `raw.records` payloads and `raw.document_text` content -- matching **diacritic-insensitively for Vietnamese** and **with stemming for English**, in one query, admin-only. Extends [[ADR 0024: A document's text is readable by dbt]], which put a document's text in Postgres and left it reachable only by hand-written SQL; related to [[ADR 0016 The Worker Seals the Control Plane Consents]], whose "the worker holds what the control plane must not" argument is why the search runs where it does. Four choices make it up, each with a rejected alternative.

**Folding is built-in SQL, not the `unaccent` extension.** The textbook answer is an `unaccent` dictionary inside a custom text-search configuration, one migration, and what every article recommends. It is ruled out by what the **gate** can run: PGlite -- real Postgres in WASM, and the only place this repo's SQL is exercised before production -- ships 21 contrib extensions at the pinned version and `unaccent` is not among them, so a search built on it would be enforced **nowhere** until a deploy. Choosing a design the offline gate structurally cannot execute makes `CLAUDE.md`'s "a green verify is not evidence" worse on purpose. So `raw.fold` is `lower(translate(normalize(t, NFC), <table>, <table>))`, core SQL identical in PGlite's PG 16 and in the managed database, at the cost of a hundred-odd characters written out by hand and pinned by two tests. A `pg_trgm` similarity search is rejected for a different reason: trigram similarity answers "looks like" rather than "contains", which for a contract reference or an invoice number is not the question being asked.

**Two GIN expression indexes, not stored generated columns.** `ADD COLUMN ... GENERATED ALWAYS AS (...) STORED` is the shorter spelling, and on `raw.records` it is a full table rewrite under `ACCESS EXCLUSIVE` -- precisely what `030_raw.sql` partitioned that table from its first migration to avoid, with the payloads already the largest thing in the database. An index on the partitioned **parent** adds no column, propagates to existing partitions and is inherited by every partition created later, so a new source is searchable with no migration -- the same property the table was partitioned for, pinned by a test that plans a query against a partition created after the migration ran.

**It runs as the tenant's dbt login, through the worker, and no grant in the model changes.** `180_document_text.sql` grants `undercroft_app` a column-scoped `SELECT` that deliberately excludes `text`, because the UI had no screen for the content and a request log is a far less controlled surface than the table. A search box is a screen for the content, so that reasoning had to be revisited rather than quietly outgrown. **Granting `undercroft_app` the `text` column is rejected**: it would put every tenant's contract text within reach of the internet-facing process for one endpoint, and make a future bug in any control-plane handler a document-disclosure bug. Instead the search goes the way `lake.query` already goes -- control plane to worker to the dbt session -- where the row-level policy keyed on `raw.tenant_of(current_user)` scopes it to one customer and the statement runs inside the console's own read-only frame, shared rather than copied because a second spelling is a second place to forget `SET TRANSACTION READ ONLY`. **The exposure is therefore unchanged**: an admin admitted to this endpoint could already have typed the equivalent `LIKE` into the Lake Console beside it and got the same bytes over the same hop. What changes is that they no longer have to, and that a Vietnamese operator gets an answer when they type without tone marks.

**The fold is length-preserving, so the snippet is the source's own Vietnamese.** `ts_headline` can only be given the folded text, so a Vietnamese operator searching their own documents would be shown their language with the tones stripped off, in their own product. So `raw.fold` maps one character to one character -- `translate` over NFC rather than `normalize(NFD)` plus strip-the-marks, which changes length **and** leaves `đ` alone, `đ` being a letter rather than a d with a mark on it. An offset found in the folded text is then valid in the NFC original, and highlighting happens in the browser through the same fold rather than as markup on the wire every reader would have to trust or escape. That property is the one thing that cannot quietly break: if folding ever changes a string's length the excerpt slides off the match and returns a wrong answer that looks like a right one, so it is pinned on both sides in SQL and TypeScript, and `scripts/fold.test.ts` fails if either table learns a letter the other does not. When no query term occurs literally -- a real match through the English stemmer -- the excerpt is the head of the text and nothing is highlighted, rather than a nearby guess, because a window on a guessed offset reads exactly like one on a found match.

Deliberately limited: 200,000 characters per value, because `to_tsvector` raises above the 1 MB tsvector ceiling and inside an expression index that error is raised by the `INSERT`, so an unguarded index would refuse to land the document it was built to find; rank across the two kinds is a heuristic, honest within a kind and merely an ordering across them; records are indexed by value rather than by key, since indexing `payload::text` whole would make a search for `name` return every record a source ever sent; and tombstones are returned **and say so**, because "which contract said this" is asked about terminated contracts more often than live ones. Consequences: one new migration plus one edited line, the two-sided shape ADR 0024 used because the ledger keys on a file's name; more index, buying a box that does not ask the reader which language a document was written in; a second fold in the browser; and English stemming applied to folded Vietnamese, which costs a little index and matches nothing a reader would notice.
