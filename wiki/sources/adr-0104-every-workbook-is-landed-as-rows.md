# ADR 0104 Every Workbook Is Landed as Rows

A landed spreadsheet now reaches a dbt model as rows, not only as one capped cell of text. Two projections join `raw.document_text` in schema `raw`: `raw.document_sheets` (one row per sheet: index, exact name or NULL, kind, visible/hidden state, container, the workbook's `date1904` flag, declared dimension, merged ranges, row count, and `complete` with a `reason`) and `raw.document_rows` (one row per non-empty row: Excel's own row number, a hidden flag, and sparse jsonb maps keyed by column letter -- `cells` with the stored strings, `formats` with non-General number-format codes, `faults` with Excel errors such as `#REF!` or `formula-uncached`). Both are keyed by content digest (`tenant_id, sha256`), so a ledger quoted in ten messages is one set of rows; a model joins `raw.documents.sha256`. It supersedes one clause of [[ADR 0028: A workbook is read in process, and extract is scheduled by backlog]] -- sheet names are now read exactly through the package's relationships -- and extends the content exception of [[ADR 0024: A document's text is readable by dbt]] to the two tables on the same terms.

Context, measured on `tai-001` (2026-10-05): \~4,240 workbooks read, 47 cut at 1,000,000 characters (issue #385), 51 refused `xlsx-unreadable` (35 of 41 digests at least 5 MB), 364 `.xls` refused, and 132 Gmail `.xlsx`/`.xlsm` parts sent as `application/octet-stream` never landed. The reader also joined a row's cells in document order, so a value after an omitted empty cell slid into the wrong column.

Decision. The platform records facts and interprets nothing: no header chosen, no type inferred, dates kept as serials beside `date1904` and their format code, merges and hidden rows recorded but never acted on; models type values with `parse_amount` and new `excel_serial_date` / `excel_serial_timestamp` macros. A cell is placed by its `r` reference (ECMA-376 §18.3.1.4); a row out of order or past XFD refuses the workbook. Inside the spreadsheet family (plus octet-stream and zip types) the container confirms the reader -- `[Content_Types].xml` for a zip, root streams for CFB -- with named refusals `workbook-password-protected`, `workbook-not-a-workbook`, `xlsb-unsupported`, `xls-biff5-unsupported`; no extension is consulted at read time. A spreadsheet extension an admin chose (`.xlsx`, `.xlsm`, `.xls`, `.xltx`, `.xltm`) lands an octet-stream file as its workbook type (`landsAs`), but the curated MIME choice still does not admit octet-stream files by name -- [[ADR 0048: A file is recognised by its type first, and a signed record is verified before it is read]] refuses to widen consent -- and [[ADR 0076: A harvest records what it left behind]] re-reads the held messages once the extension is chosen. A BIFF8 double is rendered once to its shortest round-trip decimal and an RK's ×1/100 is applied with `big.js`. Sheets and rows of a digest are replaced only after a successful parse; `ROWS_VERSION` drives a byte-reading backfill that also rewrites stale text. For #385, completeness is `document_sheets.complete` and `document_text.truncated` still describes search text only; `MAX_TEXT_CHARS` is not raised. Limits are Excel's own (1,048,576 rows, 16,384 columns, 32,767 characters, 256 sheets); the 32 MiB member ceiling stands until a streamed read replaces it under its own ADR. dbt roles select both tables under the `document_text` row policy; `undercroft_app` sees sheet counts without names and no rows; `undercroft_bi` nothing.

Rejected: a macro splitting `document_text`, one row per cell, a dense `text[]`, typed per-sheet tables with inferred types, DuckDB `read_xlsx` (inferred headed tables, network-loaded extension, native code beside `UNDERCROFT_SECRET_KEY`, no `.xls`; a secret-free container is the alternative to weigh), raising `MAX_TEXT_CHARS`, rows keyed by document, letting the curated MIME choice admit octet-stream files by name, and filling merges or dropping hidden rows on the platform's side.
