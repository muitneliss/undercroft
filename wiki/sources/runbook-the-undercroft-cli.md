# Runbook: The undercroft CLI

How to use and change the `undercroft` CLI; the decisions are [[ADR 0044: An agent reaches Undercroft as a caller]], for how it gets onto a machine [[ADR 0046: The CLI installs once, from the latest release]] and, superseding its install lines, [[ADR 0135 The Instance Serves Its Own CLI]], for signing in to a desktop install [[ADR 0096: The CLI signs in to a local install the way the browser does]], and for signing in unattended with a personal token [[ADR 0134 The CLI Signs In With a Personal Token When Nobody Is at Its Terminal]]. In this repo it runs as `task dev:cli -- <command>` (build, then `node apps/cli/dist/undercroft.mjs`). Anywhere else a person installs it from the server they sign in to: `npm install -g https://<your Undercroft>/cli/undercroft-cli.tgz`; `npm uninstall -g undercroft-cli` removes it. It needs Node 22. Every server serves the CLI of its own build there, with no sign-in, so its commands are that server's; the line is run again after the server is upgraded. The image packs it with `apps/cli/scripts/pack.ts` (the script behind `task build:cli-pack`) and names it in `UNDERCROFT_CLI_TARBALL`; a server with that unset, such as one from a checkout, serves none, even with an earlier pack lying in `apps/cli/dist/`. A server with no tarball answers 404; one whose release predates the route answers with its web page, and npm fails with `TAR_BAD_ARCHIVE`. For either, a person with access to the private repository ([[ADR 0121 Dokploy Clones the Private Repository over SSH, with a Read-Only Deploy Key]]) downloads the release the server runs (printed at the foot of every page and on the sign-in page) with `gh release download vX.Y.Z --repo muitneliss/undercroft --pattern 'undercroft-cli-X.Y.Z.tgz'` and installs the file, because npm sends no GitHub credential and a release URL given to it is a 404. Each release still attaches the tarball as `undercroft-cli-X.Y.Z.tgz` and `undercroft-cli.tgz`; `task cd:cli-upload` attaches both.

An agent gets the CLI with `npx skills add muitneliss/undercroft --skill undercroft`, and the skill installs it from the person's server too; the skills themselves, and the workflow skills beside the entry one, are covered by [[Runbook: Agent skills]]. Before its first command the agent runs `undercroft --version` and compares it with the release `skills/undercroft/references/cli.md` says it describes, installs the CLI when it is missing, asks the person before replacing a different installed release, and falls back to `npx` on the same URL when a global install is refused. That release is written once in the file's pinned block, because release-please's generic updater rewrites only the first version on a line; the 1.20.0 release, when the block was a GitHub URL, left the tarball name at 1.19.1, a 404. `scripts/skills.test.ts` fails when that pinned block holds more than one version or one other than the release's. The README pins nothing: it is an index that links to this runbook, which owns every install line.

A person creates a profile per environment (`config set-profile local --url http://localhost:3000 --allow-writes`, which only works at a terminal; against a deployed server the installed `undercroft` is run the same way, with writes left off until a person means to change something), signs in with `auth login` (email, then the emailed code), and runs commands; a missing tenant is asked for from `tenants list`. On a desktop install made by the setup wizard (`http://localhost:<port>`), there is no email and no code: `auth login` asks the server's `config.signIn`, and when signing in on this machine is the only way in, it does that with no flag, also in agent mode. On a developer's stack that also offers the emailed code, `auth login --local` chooses it; it works only on loopback and only at the exact address the install prints (`localhost` and `127.0.0.1` are two). Signing in this way never turns on writes. The first profile written becomes the default and `config use <name>` changes it; `auth status` reports the session and `auth logout` ends it. `--no-input` never prompts even at a terminal, so a missing argument is refused and a destructive command needs `--yes`; `--quiet` prints less. An agent passes `--agent` (also inferred from a non-TTY stdin/stdout) and gets exactly one JSON envelope on stdout; it signs in in two invocations (`--email`, then `--email --code`), or one on a desktop install. The envelope, codes and exit codes are in `skills/undercroft/references/cli.md`.

Unattended -- a CI job, a scheduled script, an agent with nobody to read a code -- the person mints a personal access token on the Account page and the job is given it in an environment variable; `auth login --token-env <VARIABLE>` takes the variable's name, proves the token with `session.me`, and keeps only the name and the address under the origin. Every command reads the variable again and sends `Authorization: Bearer`, so the token is in no file, argv or output, rotation is changing the variable, and revoking it on the Account page stops the next command. A `read` token is refused any command that is not a read (`lake query` and `models preview` included) with `PERMISSION_DENIED` and `needs: "write"`; a profile's `allowWrites` still applies first; a token cannot reach `account tokens …`. `auth status` reports `signedInWith: "token"` and the variable; `auth logout` forgets the variable and does not revoke the token.

`undercroft` on its own at a terminal is the home page: the title page with the sign-in form on it while signed out, the contents page (every topic and its command count) once signed in; a desktop install is signed in on this machine and goes straight to the contents; a rejected code offers a new one instead of ending the run, and a piped run still prints the help. The frames and rules are in [[Design: The CLI's home page and sign-in, drawn in text]].

Files live in `$UNDERCROFT_CLI_HOME`, else `$XDG_CONFIG_HOME/undercroft`, else `~/.config/undercroft`: `config.json` (profiles) and `credentials.json` (0600, sessions keyed by origin). `undercroft.cli.json` pins a project's profile; `--url`/`UNDERCROFT_URL` is a one-off that never allows writes; a token sign-in is kept in the same file as the variable's name and the address, never the token; `config show` explains which source decided each value and whether a session or a token signs in, and never prints either.

A new procedure needs nothing in the CLI: it needs a sentence in `apps/control-plane/src/i18n/procedures.{vi,en}.ts`, keyed by its dotted path, and a new mutation its effect in `EFFECTS` (`apps/control-plane/src/handlers/surface.ts`); a new router namespace also needs a sentence under `topics` in `apps/cli/src/i18n/{vi,en}.ts`. Those tables are typed against the router, so `task ci:typecheck` names each omission and every entry a renamed or deleted procedure left behind. A procedure the CLI calls by name (`tenants.list`, `session.me`, `session.signOut`, `config.signIn`) goes through the typed `callProcedure` in `handlers/remote.ts`, so renaming or reshaping it fails the CLI's typecheck. The build (`task build:cli`) refuses only what the compiler cannot see: an input property sharing a global flag's name. `apps/cli/src/cli.test.ts` builds the bundle into a temp dir and runs it under `node` against `startControlPlane()` from `@undercroft/control-plane/testing`. `task ci:cli-pack-check` runs the packed tarball through `npx`; `task ci:skill-check` (network) checks `npx skills` lists every published skill. The control plane's image packs the tarball in its own build stage and serves it; the `release-cli` job runs `task build:cli-pack` then `task cd:cli-upload TAG=vX.Y.Z`, attaching both names; release-please bumps the version in `skills/undercroft/references/cli.md` and `apps/cli/package.json` with the root. Troubleshooting: `CONFIG_REQUIRED` (no profile or URL, a profile that does not exist, or an unreadable config file), `AUTHENTICATION_REQUIRED` right after signing in (a different origin, e.g. `localhost` vs `127.0.0.1`), `WRITES_DISABLED` (a person must allow writes), `PERMISSION_DENIED` from `auth login` on a desktop install (the other of `localhost`/`127.0.0.1`; the message names the address), `INVALID_ARGUMENT` from `auth login --local` (not a loopback URL), `auth login` asking for an email on a desktop install (the server also offers the code, or is too old to say; pass `--local`), `CONFLICT` with `TENANT_DEACTIVATED` in its details (an admin deactivated the customer, ADR 0110; every command on it is refused until an admin reactivates it, on the web or with `tenants reactivate`), `AUTHENTICATION_REQUIRED` naming a variable (the job was not given the token's variable, or the token was revoked or expired: mint a new one), `PERMISSION_DENIED` with `needs: "write"` (a `read` token), `INVALID_ARGUMENT` from `--token-env` (a value that is not a variable name, most likely the token itself), `NETWORK_ERROR` (the URL does not answer `/trpc` as tRPC), `EACCES` on `npm install -g` (a system-wide Node; use one you own rather than `sudo`), `404` or `TAR_BAD_ARCHIVE` from `npm install` against a server (it serves no CLI: a checkout, or a release older than the route; install that release from GitHub).

Exports (ADR 0111): `bi exports create` answers with a link to every row of a saved question, a definition or a model as CSV, and the local command `bi exports download <url> --out <file>` writes it with the profile's session; the link lives 15 minutes, a cut download writes no file, and a link to another server is refused before the session is sent ([[ADR 0111 An Export Is a Link to a Streamed CSV]]).
