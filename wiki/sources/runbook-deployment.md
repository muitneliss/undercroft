# Runbook Deployment

Undercroft runs on the Dokploy instance at `lowbit.link` as a **single compose stack that clones this repository's `main` on every deploy** ([[ADR 0049: Dokploy clones the compose file from main]]), and `https://undercroft.lowbit.link` -- the control plane -- is the only public surface; the Reports division inside it is the BI and Metabase is gone ([[ADR 0020: BI is first-party, Metabase leaves the stack]]). Everything else talks over the compose network and publishes nothing: the `worker` (ingestion, dbt per tenant, the BI query runner), `minio` (the raw lake, on the `pgsty/minio` community build -- [[ADR 0050: The raw lake runs a community build of MinIO]]), `postgres`, `kestra` with its own Postgres, and four one-shot services that must exit 0 -- `minio-init`, which creates the bucket; `kestra-init`, which hands Kestra's volumes to uid 1000 (without it Kestra crash-loops with `AccessDeniedException` on `/app/storage/plugins`, no flow is ever registered, and every run arrives as `trigger: manual`); `db-migrate`, which applies `packages/db/sql` and sets the two platform roles' passwords; and `kestra-flows`, which delivers `flows/` on every deploy. Kestra runs two flows: `ingest_due` every fifteen minutes starts each due (customer, source) pair, and `extract_due` hourly at :07 starts an extract run for each pair holding landed documents not yet read into `raw.document_text`; a pair already running is a 409 both ignore.

**Two compose files, kept in step.** `docker-compose.yml` is for development and `build:`s the images and binds ports to localhost; `docker-compose.server.yml` is the file Dokploy deploys, cloned from `main` each time with no copy held in the panel, and differs in three ways, each a failure that happened once: published `ghcr.io` images (the host's checkout is `main` at deploy time rather than the release, so a `build:` there would ship code no release published and no `verify` could prove), no host ports, and a **unique network alias per service** (`undercroft-postgres`, `undercroft-minio`) used by every reference -- because a domain-bearing service joins the shared `dokploy-network`, where `postgres` and `minio` are names other projects use too, and on the old stack a Metabase authenticated against another project's database, stopped only by a password mismatch. A change made only in the development file will not survive a deploy.

**A deploy happens on a release and nowhere else.** Merging the release-please PR bumps the version, cuts a tag, builds the images, and runs `task cd:preflight → cd:deploy → cd:verify → cd:smoke` (each wrapping `scripts/dokploy.ts`); a plain push to `main` ships nothing. By hand it is the same client and the same four tasks, or `task cd:release TAG=vX.Y.Z` for the sequence, needing `DOKPLOY_API_ENDPOINT`, `DOKPLOY_API_KEY` and `DOKPLOY_COMPOSE_ID` exported and never written to a file. The API is the only channel for a change; SSH reads state and never makes one. See [[ADR 0008 Deploy on Release from CI]] and [[ADR 0023 Task Is the Mandatory Command Entrypoint]].

**The release PR is opened by a GitHub App, not `github-actions[bot]`.** Since June 2026 GitHub holds every workflow run on a PR the default token authored behind "requires approval from a maintainer", so release-please runs on an App installation token (`actions/create-github-app-token@v3`) and the workflow's own `GITHUB_TOKEN` drops to `permissions: {}`. Two repository settings feed it: the variable `RELEASE_PLEASE_CLIENT_ID` (the App's client id) and the secret `RELEASE_PLEASE_PRIVATE_KEY` (the whole `.pem`); they must come from the same App, and a rotation that misses either fails the `release` workflow at its first step. The App needs Contents and Pull requests read & write and nothing else, and must be installed on the repo; it is an App rather than a PAT because a PAT expires and makes every release read as authored by whoever minted it.

**What `preflight` proves** comes before any of that, in four checks. The panel must **clone the file rather than hold a copy**: source `git`, `https://github.com/muitneliss/undercroft.git` at `main`, compose path `deploy/compose/docker-compose.server.yml`, with auto deploy **off**, since on it would roll out every push while images change only on a release. **`main` must carry the same file as the checkout being deployed**, because the host clones `main`'s head rather than the release's commit, and a change merged while the images built would otherwise ship beside images that predate it; line endings and trailing blank lines are forgiven, nothing else. The file must name published `ghcr.io/muitneliss/undercroft-*` images, because the host deploys what a release published and never builds. And the stored command must carry `--env-file deploy/compose/.env`, `-f deploy/compose/docker-compose.server.yml` and the four pull/wait flags, since Dokploy runs it from the clone's root and writes `.env` beside the compose file. The panel used to hold a pasted copy that drifted -- once until it ran a service this repo deleted ([[ADR 0020: BI is first-party, Metabase leaves the stack]]) and three releases failed at `--wait`, and again when a merged change was never pasted and v1.26.0 stopped at `preflight` -- so there is now nothing to push: merge the file and the next release runs it. CI never writes these settings; a refusal is repaired by a person in the panel or with `compose.update`, sending only those fields because its `env` replaces the whole credential blob, and a variable a newer file needs must be in the panel's environment before the release that carries it.

**What `verify` proves** is the part worth knowing: it asks the host for the config digest each released container is actually running and compares it to what ghcr serves, because Dokploy reports `done` for a deploy that changed nothing and every smoke probe then passes against the old images. Passing `TAG=v1.2.3` makes the other side of the comparison that release's immutable manifest, so a pass means "the host runs this release" rather than "a moving pointer equals itself"; the task requires a tag, so with no release being rolled out it is `TAG=latest`. It reads which services are one-shot from the compose file's own `condition: service_completed_successfully` declarations rather than from a list it keeps -- a long-running service must be `running`, a one-shot must have **exited 0** -- and checks both kinds' digests, since a migration that exited 0 on last release's image is still the wrong thing having run.

**A deploy during a run is a stop, not a kill** ([[ADR 0051: A deploy stops a run at a safe point, and the run keeps its counts]]). Recreating the worker sends it SIGTERM. The worker tells every ingest in flight to stop at its next safe point, waits up to 45 seconds for them to settle, then exits, all inside the `stop_grace_period: 60s` the compose file allows before SIGKILL. A Google ingest reaches a safe point after every message or Drive file, so it usually stops in seconds. A run stopped that way is `failed` with *the worker was shut down while this run was in progress…* and carries the counts it really landed. Nothing needs doing: the next run carries on from there and lands nothing twice. A run the worker could not stop in time (a long Gmail or Drive listing, a download backing off on a rate limit, a dbt build) is closed by the stopping worker just before it exits, with *the worker was shut down (a deploy or a restart) before this run reached a point where it could stop safely…* ([[ADR 0056: A Drive ingest stops within one file, and a run the drain gives up on says it was cut off]]). Its `stopped` log line says `drained: false`, and `runs_cut_off` names the runs. Only a run lost with no warning (an OOM kill, a SIGKILL, a crash) is closed at the next boot, with *the worker stopped abruptly…*, logged as `runs_abandoned`. That message after a deploy is worth checking against the kernel log and `OOMKilled`. In both cases the zero counts mean the process could not write them, not that the run landed nothing.

**Every deploy, failed release, issue, pull request and red `ci` on `main` posts a card to the team's Lark group**, from `scripts/notify.ts` through `task notify:*`: `deploy.yml`'s own `notify` job reports the result and the step that stopped a failed rollout, `release.yml`'s reports a release that broke before its deploy started (and leaves the deploy out of its `needs`, so a failed rollout posts once), and `notify.yml` covers issues, pull requests and CI between releases. The webhook URL is the credential and lives only in the `LARK_WEBHOOK_URL` secret; `LARK_WEBHOOK_SECRET` adds Lark's signature check, so a leaked URL alone cannot post. An issue or PR body renders as Lark markdown -- headings as bold lines, lists, links, GitHub emoji shortcodes -- and a PR card colours its `+`/`−` line counts, but every tag in quoted text is escaped rather than obeyed and titles stay plain text, because an issue titled `<at id=all></at>` would otherwise page the whole group; Lark refuses a message with HTTP 200 and a non-zero `code`, which the job reports as a failure rather than as sent. `notify.yml` runs on `pull_request_target` so a fork's PR can post, which is safe only because it never checks out or runs the PR's code. A card that cannot post turns its own job red and never changes the result it reports on; `task notify:test` proves the wiring after a rotation. **Sync status posts there too, from the control plane rather than CI**: its once-a-minute alert tick posts a red card when a sync or model build fails -- the same failure a tenant's admins are emailed about, held for a day on repeat alike, with the vendor's reason shown exactly as written -- and a green card for the first success after it, saying since when it had been failing. Cards are in Vietnamese and link to the run in the journal; `ops.run.notice` (`sent`, `suppressed`, `recovered`) is the claim that sends each at most once. The control plane reads its own `UNDERCROFT_LARK_WEBHOOK_URL` and `UNDERCROFT_LARK_WEBHOOK_SECRET` from Dokploy's environment -- not CI's GitHub secrets, so the two may name different groups -- and unset means email only; with it set the tick runs even without email, and grants and keys, which only email carries, are then left unclaimed.

**Dokploy does not inject its variables into containers.** A variable saved in the panel is only the *source* of a value and reaches a container only if that service's `environment:` block names it; an unmapped one arrives as an empty string and fails far from the cause. The `:?set in .env` variables hard-fail the stack when unset, among them `UNDERCROFT_SECRET_KEY`, `UNDERCROFT_SESSION_SECRET`, `UNDERCROFT_PUBLIC_URL` and the several passwords. The per-source clients default to empty: the Google ingest pair and the Xero pair, plus `UNDERCROFT_GOOGLE_PICKER_API_KEY` and `UNDERCROFT_GOOGLE_PROJECT_NUMBER` for the Drive Picker on the control plane, and the worker's optional `UNDERCROFT_GOOGLE_MIN_INTERVAL_MS` pacing override. `UNDERCROFT_DBT_PASSWORD` and `UNDERCROFT_METABASE_PG_PASSWORD` are dead and should be removed from the panel if still present. Each service connects as its own role, with `db-migrate` the one service connecting as the bootstrap superuser; neither dbt nor BI has a password of its own any more, since each build and each question runs as the tenant's own login minted just before ([[ADR 0018: per-tenant roles and row-level security]]). Migrations are applied by the deploy, are idempotent and ledgered, and both apps wait on `service_completed_successfully`, so nothing starts against a schema lacking its tables; if the schema is behind, sign-in does not degrade but **stops**, with `Database schema mismatch` in the log while `sign_in_configured` still prints.

**Tracing.** Every request to the control plane or the worker answers with an `x-trace-id`, which the UI's error box, the CLI's `error.traceId` and every log line written while serving it share ([[ADR 0058: Every request is traced, into the host's shared otel-lgtm stack]]). Export to the host's shared `otel-lgtm` stack -- the `observability` project, not ours, with Grafana at `kanna-grafana.lowbit.link` -- is one line a person sets in Undercroft's Dokploy environment, `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-lgtm:4318`; the worker reaches it because the server compose attaches it to `dokploy-network`. Unset is export off, with the ids still stamped, and each service logs `telemetry_exporting` or `telemetry_export_off` at boot. `task obs:trace`, `obs:logs`, `obs:search` and `obs:host-logs` read a trace back, each finding its own credentials (`task obs:creds` checks them).

Sign-in is invite-only by Google or an emailed code ([[ADR 0010 Invite-Only Sign-In with Better Auth]]); this page carries only the production-specific part -- the Google client's redirect URIs, the origin having to match `UNDERCROFT_PUBLIC_URL` exactly, and scopes staying at `openid email profile` -- while [[Runbook Sign-In Setup]] is the walkthrough. The first admins come from `UNDERCROFT_SUPERADMINS` in Dokploy's environment, comma-separated, named more than one because a single address is a single point of lockout ([[ADR 0013 Superadmins Named in the Environment]]). **Rollback** is `IMAGE_TAG=vX.Y.Z` in the panel and a redeploy -- the release on screen is printed at the foot of every page including sign-in, so it can be read by someone who cannot get in -- and `IMAGE_TAG` must go back to `latest` once the fix ships, or the next release fails `verify` for the right reason. The compose file does not roll back with it: the host clones `main`'s file whatever `IMAGE_TAG` says, so a file change the older images cannot run must be reverted on `main` too. Kestra has no domain by design; its flows are baked into the control-plane image and delivered every deploy, `{{ envs.x }}` resolves from `ENV_X` rather than `KESTRA_X`, and Kestra silently 401s every request when a password fails its complexity rules. Recorded gaps: the real `pg` + `search_path` path and a real login are proven in the Docker tier rather than the offline gate, and the raw lake is not in a backup set -- it is object storage with versioning and replication, and the one layer that cannot be regenerated.
