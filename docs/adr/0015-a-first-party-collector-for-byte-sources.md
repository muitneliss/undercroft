# 15. Gmail and Drive are a first-party collector, not a connector spec

- Status: Accepted
- Date: 2026-09-18

## Decision

Gmail and Google Drive are ingested by code in `apps/worker/src/services/google/`, not by a
YAML file in `specs/connectors/`. They enter through the same `runIngest` door, so no caller
has to know which kind of source it asked for.

`packages/contracts/src/connectorSpec.ts` is **not** extended with a binary request kind.

## Why the spec cannot express them

The declarative connector format reads JSON records over a text fetcher. Three things about
these two sources sit outside that, and none is a detail:

- **`HttpResponse.text` is a string.** `createFetcher` consumes every body with
  `response.text()`, so the bytes of a PDF are gone by the time anything downstream sees it,
  and re-encoding the string does not give them back.
- **Neither request shape is expressible.** Gmail's `labelIds` is AND rather than OR, so a
  selection of three labels is three paged queries unioned client-side; Drive's content
  arrives from `?alt=media` rather than from a JSON envelope. No pagination kind or path
  extractor describes either.
- **`readEntity` yields `payloadText`.** A binary yield cannot use it, and `loadStreamToRaw`
  decodes every journalled object as JSON text for `payload jsonb` — a PDF on that path is
  mojibake in a jsonb column.

## Options rejected

**Add a `download` request kind to the spec.** It would mean a bytes channel on the
`Fetcher` seam that four working connectors do not need, a second paced-and-retried fetch
path beside `fetchJson`, a `RawRecordOut` that is sometimes not a record, and a JSON schema
regenerated by a step the gate does not run. The format would grow for exactly two sources
and every future reader would carry the complexity.

**Land through the lake write API as an external caller**, which is the letter of ADR 0004's
release valve. Rejected on where the credential would have to live: an external caller needs
a token, and the only process that may open a sealed credential is the worker, because it is
the only one holding `UNDERCROFT_SECRET_KEY`. Putting the collector outside the worker means
either a second holder of the master key or a credential travelling further than it must.

## Consequences

- **The valve is taken inside the worker.** ADR 0004 said what a spec cannot express is
  landed by a caller of the lake API; this is that, with the caller in the same process as
  the store. The property preserved is ADR 0005's: the credential never leaves the process
  that can open it.
- **`raw.documents` is used for the first time.** It has existed since `030_raw.sql` with
  grants in `040_grants.sql` and no TypeScript behind it. Nothing new was designed for
  bytes; a table the schema already anticipated was filled in.
- **A PII boundary is now load-bearing and is written down.** `raw.documents` is granted to
  `undercroft_dbt`, so its columns — `lake_key` included — are one `dbt run` from a
  dashboard. Opaque provider ids, timestamps, enumerated types and counts go in the row;
  anything a human wrote (a filename, a subject, an address, a folder name) goes in the lake
  manifest, which dbt and BI cannot reach. `landDocuments` takes them as two separate
  arguments so the split is visible at every call site. Recorded in `.claude/rules/pii.md`.
- **What the runtime got right is not rebuilt.** Pacing, retry and back-off come from
  `@undercroft/core` on an injected `Clock`, so a 429 is exercised in the offline gate with
  nothing sleeping.
- **A third source of this shape would be a third module.** That is the accepted cost. If a
  fourth arrives, the question of a byte-capable spec format is worth reopening — with a new
  ADR superseding this one, not an edit to it.
